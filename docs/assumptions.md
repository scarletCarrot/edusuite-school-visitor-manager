# Assumptions and resolved questions

Each entry records a gap in the problem statement, what I decided, why, and what changes if the decision is
wrong. IDs are referenced from [spec.md](spec.md). Keep this file current: add an entry whenever a new decision
is made.

| ID | Open question | Decision / assumption | Reasoning | Impact if wrong |
|---|---|---|---|---|
| A1 | How many gates and desks? | One main gate with one front-desk screen, possibly staffed by several guards, each with their own account. | The statement mentions "our main gate" only. | Several gates would need a gate field on visits and a per-gate desk view. The data model and API change slightly; the lifecycle does not. |
| A2 | What device does the guard use? | A desktop or tablet browser with network access at the gate. | Lowest-cost option; no app installs. | A phone-only guard would need a mobile layout review. If there is no reliable network, an offline mode is a large change (risk R3). |
| A3 | How is the visitor's identity checked? | The guard checks an ID by sight; the system stores no ID numbers or photos. | Data minimisation under RA 10173; the statement does not ask for identity records. | If the school must record ID numbers, add an encrypted field, a retention rule and an update to the privacy notice. |
| A4 | What is the "visitor pass"? | The numbered lanyard cards already in use. The guard enters the card number at check-in. | The cards already exist and guards know the process; there is no printer at the gate. | If a printed or QR pass is required, add a print view or QR generation (ranked Should/Could). The `pass_number` field still holds the code. |
| A5 | What if a walk-in cannot name an employee, or the employee has no account? | The guard picks the relevant office's account (for example the admin office), which is set up as an employee. | Every walk-in needs someone accountable to vouch for them. | If offices need shared inboxes with several responders, add group hosts. |
| A6 | How long does a host have to answer, and what happens if they don't? | 10 minutes (configurable). After that the visit is `TIMED_OUT` and entry is **not** granted. The guard may register again to notify again, or pick another host. | Safeguarding on a K-12 campus: deny by default. 10 minutes is long enough to step out of a class, short enough that the visitor is not left waiting. | If the school prefers escalation, add a step that notifies the admin office before the timeout (Could). If 10 minutes is wrong, change `visitors.host-response-timeout`. |
| A7 | What does "overstayed" mean? | Checked in more than 4 hours ago (configurable), including anyone still checked in from a previous day. | Most visits (meetings, parents, deliveries) are well under half a school day; a single rule is easy to explain. | If the school wants a per-visit expected departure or a campus closing time, add an `expected_until` field and change one method. |
| A8 | Can a pre-registration be used on another day or for several days? | It is valid only on its date. A visitor who comes on a different day goes through the walk-in flow. | Keeps the expected list accurate and stops old pre-registrations from being used to enter. | Recurring visitors (tutors, contractors) would need multi-day or recurring pre-registrations. |
| A9 | Does the host need to confirm again when a pre-registered visitor arrives? | No. Pre-registering is the confirmation; the host gets an "arrived" notification. | The statement requires confirmation only for visitors who were not pre-filed. | If the school wants a second confirmation, pre-registered check-in would go through `AWAITING_HOST` too. |
| A10 | Are parents visitors? | Yes, when they enter campus for a meeting or errand. Student pick-up and release is out of scope. | Pick-up has its own safeguarding rules (authorised guardians) that do not fit this lifecycle. | A pick-up module would be a separate feature. |
| A11 | Where does the employee list come from? | Accounts are seeded. User management and an HR sync are out of scope. | The exam allows seeded users; 150 employees change rarely. | Needed before go-live (spec §12). |
| A12 | What can the principal / admin do? | Read-only: today's visits, the on-campus view and the audit trail. Admin accounts do not host visitors. | Separation of duties; the statement only asks the principal to know who is on campus. | If admins must host visitors or override decisions, allow several roles per user and add an override action that is audited. |
| A13 | How do we reach employees outside the app? | Every employee has a school email and a mobile number on file. Both channels are simulated (logged). | The statement suggests email and SMS; the exam says to simulate them. | Employees without a phone or email would be reached in-app only. Each channel already fails independently. |
| A14 | Which time zone defines "today"? | Asia/Manila. Timestamps are stored in UTC. | Single Philippine campus. | Multi-region use would need a time zone per tenant. |
| A15 | How long is visitor data kept? | One year, then visitor name and phone are anonymised. Not built yet; to be confirmed by the school's DPO. | RA 10173 requires a defined, proportionate retention period. A year covers incident follow-up and a school year. | A different period is a configuration value in the purge job when it is built. |
| A16 | Which visitor details are required? | Name and purpose are required; mobile number is optional. | Minimum needed to identify the visit and inform the host. | If the school needs a contact for every visitor (for example for incident tracing), make phone required. |
| A17 | How are groups handled (for example 3 people from a supplier)? | Each person is registered and gets their own card. | Every person on campus must be counted and must check out. | A bulk "group" entry would be a UX shortcut on top of the same model. |
| A18 | What if the card is not returned? | The guard can check the visitor out from the on-campus list. The audit trail records who closed the visit and when. | Better a closed record with a known closer than an open record forever. | If the school needs to separate "left" from "closed by guard", add a check-out reason. |
| A19 | Can a guard confirm on a host's behalf, for example after a phone call? | No. Only the named host can confirm or decline. | The statement says "that employee must confirm". Letting guards confirm would bring back the phone-around process with no proof. | If needed, add a "confirmed by phone" action for guards that names the host and is audited. |
| A20 | What if a walk-in is approved but the visitor leaves before getting a card? | The visit stays `APPROVED` with no pass; it drops off the desk list the next day. | Rare, and harmless: no pass was issued, so they were never on campus. | If it matters for reporting, add an "abandoned" outcome. |
| A21 | How do users sign in? | Seeded username and password, HTTP Basic, stateless. | The exam allows simple authentication; the server still enforces every rule. | Production uses school SSO (spec D7). |
| A22 | Which language does the UI use? | English. | English is the language of school administration in the Philippines. | Filipino labels would need i18n of the UI text only. |
| A23 | How many visitors per day, and how much load? | 40–80 visitors per day, 1–3 desk screens, 150 employees. | Given in the exam context. | At much higher volume, replace polling with push and add indexes (spec §6, D8). |
